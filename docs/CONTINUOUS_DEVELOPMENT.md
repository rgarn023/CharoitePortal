# Charoite continuous development

Coordination PR [#9](https://github.com/rgarn023/CharoitePortal/pull/9) stays open. Its branch, `automation/charoite-continuous-development`, holds this protocol and `.github/automation/development-state.json`. Publish engineering changes through separate, short-lived PRs from current `main`. The cross-build watches changes to its real inputs on `main`. A commit to the coordination branch cannot validate a provider change.

## Which work runs when

* An independent hourly task opens a batch only when three UTC clock hours have elapsed since the last batch, by setting `event_batch_utc` to the current UTC hour (ISO `YYYY-MM-DDTHH`) under the lock. Preserve this value throughout that batch. Only the hourly task or an explicitly requested manual start may open a batch.
* The existing provider postbuild verifies the upstream repository, source repository, branch, workflow path, event, attempt, SHA and completed status. Its separate comment job serializes publication on PR #9. It sends one build completion per three-hour batch. An expired or exhausted batch hands further work to the hourly task. Events never extend their own batch. Build IDs, the ledger and the bot's existing comments prevent duplicate signals.
* A new trusted completion comment may start the next engineering cycle immediately. Fetch the original comment by ID. Require a newly created top-level comment on PR #9 authored by GitHub Actions or by the repository owner, the exact completion marker, and an independently verified matching run. A test marker is read-only. Lifecycle events, reviews, ordinary discussion, ledger commits, coordination commits, unrelated workflows and duplicate deliveries do not start engineering. Never reply on PR #9 to induce another run.

## Shared lock and outstanding work

1. Read the handoff on `main`, the ledger, the relevant PRs, and actual Actions jobs, logs and artifacts. Existing claims or active cross-builds take precedence. To change shared state or code, claim `owner` using a unique token and the observed blob SHA with GitHub's file update. A conflict or another owner means yield. Re-read ownership before every engineering mutation. Never force a ref or steal a lock.
2. `processed_run_ids` records completed analysis of a build. `pending_validation` separately tracks a proposal and its next transition. Record the source run, PR/branch, head SHA, phase and merged main SHA as applicable. A processed source run can still have a PR awaiting verification, merge or main CI. Resume that transition under the lock even when no new run ID exists. Reconcile GitHub's actual PR status, commits and runs after an interruption. Never create a second proposal for an existing transition.
3. For one evidence-supported milestone, publish code on a new engineering branch from current `main` and open a PR targeting `main`. Check its diff, test the behavior and wait for the applicable GitHub checks on the reviewed revision. For a safe, in-scope CI or Charoite Next change with passing checks, merge the reviewed head using GitHub's expected head SHA. Respect repository review and branch protection. Leave unrelated proposals alone. The coordination PR itself must remain open.
4. Record the merge SHA and watch the existing workflow for changed provider inputs. Release the lock after saving the transition so the completion event can take over. If the next run already completed, the same lock and ledger decide which worker picks it up. Read diagnostic output, including nonblocking steps, before recording results. New checkpoints refer to [cross-build #143](https://github.com/rgarn023/CharoitePortal/actions/runs/44310229156) and later. Account for a rerun of an already recorded ID without repeating its engineering change.
5. An hourly check during an open batch reads only the ledger and targeted CI status, unless it must resume outstanding validation or notify the owner of a failure. A new scheduled engineering milestone starts only when opening a new three-hour batch. The hourly task first resumes an outstanding PR or missed signal. If there is no new build and no pending PR, it can start one evidence-supported next milestone from the verified handoff. Duplicate suppression applies to an already performed change, not to new work. Do not rebuild identical inputs, retry an unchanged failure, or manufacture an event. Persist blocked work with the evidence needed to resume. Report a stuck lock or a required owner decision.

## Evidence, data and cost

Each cycle reads the actual job logs, checks uploaded artifacts and records verified progress in `docs/CURRENT_HANDOFF.md` on `main`. The provider workflow publishes PE candidates and diagnostics only. A nonblocking probe may fail inside a successful job. Verify a signed experimental APK and link its producing run/artifact before asking for a phone test. The v1.0 baseline is 31%. Increase it only for a demonstrated functional milestone.

Use the existing subscription, public standard GitHub-hosted Ubuntu runners and fresh CI scratch. Preserve every existing Wine generation, prefix, rootfs, environment, game, save and all app data for `com.charoite` and `com.charoitx`. Do not activate paid services, credentials or GPU/larger runners. Stop for an actual cost, risky data change or necessary phone consent. Notify through ChatGPT for completed cycles, significant fixes, intervention failures, verified APKs and necessary owner actions. Link the main handoff first.
